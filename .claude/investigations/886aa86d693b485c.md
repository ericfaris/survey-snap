## Summary

`survey-snap-app-1` is not actually crashing. Every restart in the log completes with `✓ Ready in ...ms` right after the "npm error" block, meaning the app comes back up healthy each time. The "npm error path /app ... signal SIGTERM" lines are npm's own noisy error-reporting when its wrapped child process is killed by `SIGTERM` — which is exactly what happens on every `docker compose build/up`/restart during a redeploy. The repeated-error detector is picking up normal, successful redeploy cycles as if they were crash loops.

The redeploys themselves are being triggered unusually fast: git history shows two automated "sentinel fix: base-image-refresh" commits (`9a5e44f`/`23d44b1`, ~7 minutes apart) pushed to `main` by an automated bot, plus the `#3` OS-package-upgrade commit. Each push to `main` runs `.github/workflows/test.yml`'s `deploy` job, which POSTs to a local `lab-sentinel` service (`http://127.0.0.1:7891/api/deploy`) that does `docker compose build/up` against `survey-snap-app-1`. That produces the exact cadence in the logs: start at 12:48:31, killed 12:53:24 (5 min later), restart 12:54:06, killed 12:55:05 (~1 min later), restart 12:55:49 — closely-spaced redeploys from closely-spaced pushes, not application instability.

## Evidence

- `docker-compose.yml:9` — `restart: unless-stopped`, no `healthcheck:` anywhere in compose or `Dockerfile`, so nothing in Docker's own health logic is killing the container.
- `Dockerfile:58` — `CMD ["npm", "start"]`, and `package.json:8` — `"start": "next start -H 0.0.0.0 -p 3000"`. npm is the container's PID 1; when Docker sends it `SIGTERM` (on a `compose up`/restart), npm relays it to the `next start` child and then logs the child's death as `npm error command failed` / `npm error signal SIGTERM`, even though this is a routine, expected shutdown — not an application-level failure.
- Logs: each `npm error ... signal SIGTERM` block is immediately followed by a clean restart and `✓ Ready in ...ms` (e.g. lines timestamped `12:53:24` → `12:54:06`/`12:54:07`, and `12:55:05` → `12:55:49`), confirming the app itself never actually broke.
- `npm error Log files were not written due to an error writing to the directory: /tmp/.npm/_logs` — a secondary symptom of the same event: `Dockerfile:28` sets `HOME=/tmp`, and npm tries (and, due to how it's killed mid-write, sometimes fails) to flush its error log there. This is cosmetic, not causal.
- `.github/workflows/test.yml` `deploy` job — triggers a `lab-sentinel` deploy (`docker compose build/up` + health-check) on every push to `main`.
- Git log: `23d44b1 sentinel fix: base-image-refresh on survey-snap-app-1 (#2)` and the earlier duplicate attempt, plus `eac89a0` removing an accidentally-committed `.claude/scheduled_tasks.lock` — evidence of an automated bot pushing to `main` on a short cadence, each push causing another redeploy/restart of this exact container.
- No `SIGTERM`/`process.on(...)` handling anywhere in the app source, and no `tini`/`init: true` in `docker-compose.yml` — the container has no graceful-shutdown path, so npm's default (noisy) reaction to the kill signal is all that's logged.

## Suggested fix

This is a false-positive-leaning incident: no code fix is needed for a real bug, but two things are worth doing to stop it from re-tripping the alert and to make redeploys cleaner:

1. **Bypass npm as the container entrypoint.** Change the `Dockerfile`'s `CMD` (or the `start` script) to exec the Next.js binary directly — e.g. `CMD ["node_modules/.bin/next", "start", "-H", "0.0.0.0", "-p", "3000"]` — instead of `CMD ["npm", "start"]`. With npm out of the process tree, `SIGTERM` goes straight to the `next start` process, which exits quietly on shutdown; there's no npm wrapper left to log a spurious "npm error" (and the `/tmp/.npm/_logs` write-failure line disappears too, since npm's error-logging path is never invoked on a clean shutdown).
2. **Optionally add `init: true`** to the `app` service in `docker-compose.yml` so a minimal init process reaps signals correctly regardless of which command is PID 1 — cheap insurance alongside step 1.
3. Consider slowing/batching the sentinel bot's auto-commits to `main` (or adding a short debounce in `lab-sentinel` before redeploying) so back-to-back pushes don't each force an independent restart within the same minute — that's what produced the tightest gap in these logs (12:55:05 restart only 44s after the previous one came up at 12:54:07... actually 56s after Ready).

With change (1) in place, routine redeploys will no longer emit `npm error` lines at all, so this detector will only fire on genuine crashes going forward.
